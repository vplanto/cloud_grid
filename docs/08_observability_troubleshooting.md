## Питання для розминки

<details markdown="1">
<summary><b>1. Чому вебсервіс зі стабільною середньою затримкою (Mean) у 20 мс здатний водночас змушувати кожного десятого користувача чекати відповіді понад 3 секунди?</b></summary>

Розподіл затримок у мережевих системах має асиметричний **важкий хвіст (Long Tail)**, на відміну від симетричного дзвоноподібного розподілу Гаусса.

Поодинокі важкі запити, паузи збирача сміття (Garbage Collector), мережеві колізії чи очікування блокувань у базі даних розчиняються в масиві мільйонів швидких відповідей. Середнє арифметичне маскує системну деградацію. Об'єктивну оцінку користувацького досвіду дають лише перцентилі: **P95, P99 та P99.9**.
</details>

<details markdown="1">
<summary><b>2. Якщо Pod у Kubernetes перейшов у стан CrashLoopBackOff, чому команда kubectl logs &lt;pod&gt; часто повертає порожній вивід?</b></summary>

За замовчуванням `kubectl logs` читає стандартний вивід **поточного контейнера**, який щойно перезапустився й ще не встиг записати жодного рядка.

Щоб переглянути логи попереднього екземпляра, який зазнав аварії, використовують прапорець `--previous`:
`kubectl logs <pod> --previous`
</details>

## 1. Три стовпи спостережуваності (The Three Pillars)

Спостережуваність (**Observability**) — це здатність визначати внутрішній стан системи на основі аналізу її зовнішніх сигналів телеметрії.

```
                  ТРИ СТОВПИ СПОСТЕРЕЖУВАНОСТІ
     ┌──────────────────┬──────────────────┬──────────────────┐
     │     METRICS      │       LOGS       │      TRACES      │
     │   (Prometheus)   │  (Elastic/Loki)  │  (Jaeger/Tempo)  │
     ├──────────────────┼──────────────────┼──────────────────┤
     │ Часові ряди      │ Структуровані    │ Граф проходження │
     │ (Числова         │ записи подій     │ запиту крізь     │
     │ агрегація)       │ (JSON Context)   │ мікросервіси     │
     ├──────────────────┼──────────────────┼──────────────────┤
     │ Сигналізують про │ Пояснюють        │ Локалізують      │
     │ факт аномалії    │ причину збою     │ джерело затримки │
     │ (швидкий алерт)  │                  │ чи обриву        │
     └──────────────────┴──────────────────┴──────────────────┘
```

1. **Метрики (Metrics):**
   * Числові значення, оптимізовані для агрегації та збереження в Time-Series DB.
   * Типи: **Counter** (монотонно зростаючий лічильник), **Gauge** (миттєве значення: використання CPU, пам'ять), **Histogram** (розподіл тривалості запитів за кошиками/buckets).
   * **Перевага:** Мінімальний обсяг збереження; швидка побудова дашбордів і тригерів для сповіщень (Alertmanager).
   * **Вибух кардинальності (Cardinality Explosion):**
     * *Системна природа:* Кожна унікальна комбінація міток (Labels) породжує окремий часовий ряд у пам'яті. Запис динамічного значення (`user_id`, `trace_id` чи сирого URL) у мітку на кшталт `http_requests_total{user_id="12345"}` генерує мільйони унікальних рядів. Результат — вичерпання RAM і падіння сервера моніторингу через OOM.
     * *Архітектурне правило:* Метрики повинні мати лише низьку, фіксовану кардинальність (`http_status`, `method`, `environment`). Усі унікальні ідентифікатори передаються виключно в **структурованих логах або спанах трасування**.
2. **Логи (Logs):**
   * Хронологічний текстовий запис події з точним таймстемпом.
   * **Слабкість звичайного тексту:** Текстовий рядок `User 42 failed to pay` вимагає складного парсингу регулярними виразами.
   * **Стандарт:** **Структуровані JSON-логи** з чіткими полями метаданих (`trace_id`, `user_id`, `http_status`).
3. **Трасування (Distributed Traces):**
   * Механізм зв'язування дій користувача в інтерфейсі з ланцюжком викликів бекенд-сервісів, запитів до баз даних і повідомлень у брокерах черг.

## 2. Математика затримки: асиметрія розподілу

Розподіл затримок у хмарних застосунках завжди асиметричний через довгий шлейф аномалій (**Long Tail Latency**):

```
Кількість
запитів
  │       P50 (Медіана: 15 мс)
  │        ▼
  │      ┌───┐
  │     ┌┘   └┐
  │    ┌┘     └┐           P95 (120 мс)     P99 (2.5 с)
  │   ┌┘       └──┐             ▼                ▼
  └───┴───────────┴─────────────┴────────────────┴────────────► Час (мс)
```

### Перцентилі (Quantiles):
* **P50 (Медіана):** 50% запитів обробляються швидше за вказане значення. Відображає базовий стан системи за нормальних умов.
* **P95 / P99:** 95% або 99% запитів виконуються швидше за поріг. Демонструє затримку під час сплесків навантаження та локальних мережевих колізій.
* **P99.9 (Три дев'ятки):** Досвід одного клієнта з тисячі. Зазвичай це найважчі транзакції з найбільшими кошиками чи складною бізнес-логікою.

### Мультиплікація затримок у мікросервісній мережі:
Коли для формування однієї відповіді сервіс паралельно опитує **$N = 50$ мікросервісів**, кожен із яких має ймовірність деградації $P99 = 1\% (0.01)$:

$$P(\text{хоча б один сервіс деградує}) = 1 - (1 - 0.01)^{50} = 1 - (0.99)^{50} \approx \mathbf{39.5\%}$$

**Математична закономірність:** Навіть за індивідуальної надійності 99% для кожного окремого компонента **майже 40% загальних запитів зазнають деградації через очікування найповільнішої гілки**.

## 3. Анатомія розподіленого трасування (Distributed Tracing)

Розподілене трасування розбиває життєвий цикл запиту на ієрархічне дерево операцій:

```mermaid
gantt
    title Життєвий шлях запиту (Trace ID: 4bf92f...)
    dateFormat X
    axisFormat %s ms

    section API Gateway
    HTTP POST /order           :0, 100
    section Auth Service
    JWT Validation             :5, 25
    section Order Service
    Create Order Record        :30, 95
    section PostgreSQL
    INSERT INTO orders         :35, 60
    section Payment Service
    Charge Credit Card         :65, 90
```

### Базові поняття:
1. **Trace (Трейс):** Повний шлях запиту крізь розподілену інфраструктуру. Позначається глобальним `TraceID`.
2. **Span (Спан):** Окремий відрізок роботи всередині конкретного сервісу. Містить:
   * Назву операції (наприклад, `SELECT FROM users`).
   * Час старту та тривалість виконання.
   * **Attributes:** Структуровані пари ключ-значення (`http.status_code = 200`, `db.statement = ...`).
   * **Span Events:** Точкові внутрішні події (помилки, винятки).
3. **SpanContext:** Метадані для збереження причинно-наслідкового зв'язку під час передавання запитів мережею:
   * **W3C Trace Context:** Стандартизований заголовок `traceparent`:
     `traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`
   * **Baggage:** Користувацькі мітки контексту (наприклад, `tenant_id=enterprise_42`), які автоматично транслюються крізь усі спани графа викликів.

### Стратегії семплювання (Sampling Strategies):
Збір 100% трейсів у системі під навантаженням 100 000 RPS створює надмірний оверхед на диски й мережу (**Telemetry Tax**). Для оптимізації застосовують фільтрацію:

* **Head-based Sampling:** Рішення про запис ухвалюється на вході в систему (на рівні API Gateway), наприклад для фіксованих 2% випадкових запитів.
  * *Обмеження:* Рідкісні збої, що виникають глибше в системі на несемпльованих запитах, втрачаються безслідно.
* **Tail-based Sampling:** Дані тимчасово буферизуються в пам'яті колектора (OpenTelemetry Collector). Рішення про збереження ухвалюється **після завершення транзакції**:
  * Запити з помилками `HTTP 5xx` або затримкою понад $2000$ мс зберігаються на 100%.
  * Успішні типові виклики `HTTP 200` зберігаються на рівні 0.1%.

### Аномалія Clock Skew (Дрейф системних годинників):
У розподіленому кластері системні таймери вузлів мають мікророзходження навіть за активного демона NTP (дрейф становить кілька мілісекунд):
* *Сутність проблеми:* Якщо сервіс А (вузол 1) викликає сервіс Б (вузол 2), дочірній спан із вузла 2 може зафіксувати мітку початку раніше, ніж стартував батьківський спан на вузлі 1 (виникає ефект «виклику з минулого»).
* *Вирішення:* Сервери збору трейсів (Jaeger/Tempo) коригують часові зміщення на основі мережевого RTT (Round-Trip Time). Точна синхронізація через NTP/PTP на фізичних хостах залишається обов'язковою вимогою до інфраструктури.

## 4. Централізоване збирання логів: від контейнера до сховища

Логування в контейнеризованому середовищі базується на потоковій моделі передавання даних:

```mermaid
flowchart LR
    POD["Pod Container<br>(stdout / stderr)"] --> CRI["Container Runtime<br>(JSON file on node)"]
    CRI --> DAEMON["Node Agent<br>(Fluentbit / Promtail)"]
    DAEMON --> QUEUE["Message Buffer<br>(Kafka / Redis)"]
    QUEUE --> STORE["Log Store<br>(Elasticsearch / Loki)"]
    STORE --> UI["Dashboard UI<br>(Kibana / Grafana)"]

    style POD fill:#1e3a5f,color:#fff
    style DAEMON fill:#1e293b,color:#fff
    style QUEUE fill:#854d0e,color:#fff
    style STORE fill:#064e3b,color:#fff
```

### Стандартизація виводу через stdout/stderr:
Згідно з принципами **12-Factor App**, застосунок у контейнері делегує керування логами зовнішньому середовищу:
1. Застосунок спрямовує структуровані логи в потоки `stdout`/`stderr`.
2. Демон `containerd` перехоплює потік і зберігає його в локальний файл ноди (`/var/log/pods/...`).
3. Агент **Fluentbit** (як DaemonSet) зчитує файл, додає метадані Kubernetes (назва пода, неймспейс, мітки) і пакетами надсилає записи до централізованого сховища.

### Ефект «Noisy Neighbor» та Write Backpressure:
Пряме використання stdout несе прихований ризик блокування виконання коду:
* *Механізм:* Виклики на кшталт `print()` у Python або `log.info()` у Java викликають системний виклик ядра `write(1, ...)` до файлового дескриптора stdout. Якщо агент збору логів не встигає спорожняти буфер або нода зазнає дискового перевантаження (`DiskPressure`), буфер сокета чи пайп `containerd` переповнюється.
* *Наслідок:* Системний виклик `write()` переходить у режим **синхронного блокування (Blocking I/O)**. Обчислювальні процеси замість корисної роботи простоюють в очікуванні звільнення буфера виводу.
* *Архітектурне рішення:* У навантажених системах запис логів має відбуватися **асинхронно через неблокуючий кільцевий буфер у пам'яті (Non-blocking Ring Buffer)**. У разі переповнення черги надлишкові записи відкидаються, зберігаючи стабільність бізнес-операцій.

## 5. Довідник з діагностики подів у Kubernetes

Аналіз поведінки пода починається з команди детального інспектування: `kubectl describe pod <name>`:

| Стан Pod | Першопричина | Алгоритм діагностики та локалізації |
| :--- | :--- | :--- |
| **ImagePullBackOff** | Kubelet не може завантажити образ контейнера | Перевірити точність назви образу й тегу; перевірити наявність секрету авторизації `imagePullSecrets` для приватного реєстру. |
| **CrashLoopBackOff** | Процес у контейнері завершується аварійно (Exit Code != 0) | Виконати `kubectl logs <pod> --previous`. Перевірити змінні оточення, наявність конфігурацій та доступність бази даних під час ініціалізації. |
| **OOMKilled (Exit 137)** | Споживання оперативної пам'яті перевищило директиву `resources.limits.memory` | Перевірити статус у виводі `kubectl describe pod` (шукати `OOMKilled: true`). Збільшити memory limit або усунути витік пам'яті (Memory Leak) у коді. |
| **Pending** | Планувальник (Kube-Scheduler) не може виділити вузол під под | Перевірити секцію `Events` у виводі `kubectl describe pod`. Причинами зазвичай є нестача CPU/RAM під `requests`, або невідповідність селекторів `NodeSelector`/`Taints`. |
| **Node NotReady** | Kubelet припинив надсилати сигнали доступності до Control Plane | Перевірити мережевий стан хоста, вільне місце на диску (`DiskPressure`) та відгук рантайму containerd. |

## 6. Практичний місток: зв'язок із лабораторним курсом

Матеріали лекції є безпосереднім підґрунтям для виконання **Етапу 5 (Chaos & FinOps)** лабораторного курсу:

* **Впровадження W3C Trace Context у симулятор:**
  * Студенти модифікують воркери Монте-Карло, транслюючи заголовок `traceparent` від API-шлюзу до обчислювальних потоків розрахунку ліній IEEE-118.
  * У **Jaeger UI** візуалізується повний граф виконання: декомпозиція загального часу на генерацію псевдовипадкових чисел, матричні обчислення та серіалізацію результатів.
* **Трасування крізь межу процесів у Python (`multiprocessing.Pool`):**
  * *Системне обмеження:* Для подолання GIL симулятор створює пул процесів через `multiprocessing.Pool`. За замовчуванням OpenTelemetry зберігає `SpanContext` у контекстних змінних потоку (`contextvars`). Під час системного виклику `fork()` пам'ять дублюється, проте прив'язка контексту трасування втрачається.
  * *Реалізація в коді:* Функція воркера `simulate_trials_chunk` приймає `traceparent` як явний параметр у кортежі `args`. Усередині воркера виконується явне відновлення контексту:
    ```python
    from opentelemetry.trace.propagation.tracecontext import TraceContextTextMapPropagator

    # Ручне відновлення контексту в ізольованому процесі воркера
    context = TraceContextTextMapPropagator().extract(carrier={"traceparent": traceparent_str})
    ```
  * Після цього спани, згенеровані воркерами на ядрах CPU, коректно відображаються в Jaeger як нащадки первинного запиту від API Gateway.
* **Бенчмаркінг перцентилів під стрес-тестуванням:**
  * За умов ін'єкції затримок (через **Toxiproxy** або дискове навантаження Noisy Neighbor) студенти фіксують графіки **P50 проти P99 latency** замість усереднених значень.
  * Досліджується прямий вплив важкого хвоста затримок на сумарну пропускну здатність (Throughput) кластера.

## Підсумок лекції

1. **Середнє арифметичне спотворює реальність:** Реальний стан розподіленої системи з асиметричним розподілом затримок демонструють виключно перцентилі (**P95, P99, P99.9**).
2. **Каскадна деградація:** Затримка одного компонента в ланцюжку з 50 мікросервісів призводить до того, що до 40% користувачів відчувають уповільнення системи.
3. **W3C Trace Context уніфікує телеметрію:** Стандартний заголовок `traceparent` забезпечує наскрізну видимість запиту від користувацького кліку до воркерів на обчислювальних нодах.
4. **Діагностика через Exit Codes:** Точне розуміння кодів завершення контейнерів (Exit Code 137 OOM проти помилок коду 1/2) локалізує проблему за перші секунди інциденту.

## Контрольні питання

<details markdown="1">
<summary><b>1. Чому Tail-based Sampling у навантажених системах дає якіснішу картину деградацій, ніж Head-based Sampling?</b></summary>

Під час **Head-based Sampling** вибір запису трейсу відбувається на старті (на API Gateway), коли фінальний статус операції ще невідомий. Якщо ймовірність збою становить 0.01%, то за 1% фіксованої вибірки абсолютна більшість критичних помилок пройде повз моніторинг.

**Tail-based Sampling** буферизує спани в пам'яті колектора до повного завершення ланцюжка викликів. Це дозволяє зберегти **100% повільних запитів (P99) та відповідей із помилками (HTTP 5xx)**, відкидаючи до 99.9% одноманітних успішних викликів і зберігаючи ресурси сховища.
</details>

<details markdown="1">
<summary><b>2. Як за системними метриками розрізнити монотонний витік пам'яті (Memory Leak) від короткочасного сплеску навантаження до спрацьовування OOM-killer (Exit Code 137)?</b></summary>

У разі **Memory Leak** метрика використання пам'яті (`container_memory_working_set_bytes`) утворює постійно висхідну лінію або характерну пилкоподібну форму, яка не спадає навіть у години мінімального навантаження.

Під час **раптового сплеску навантаження** рівень пам'яті залишається стабільним аж до моменту різкого вертикального стрибка, який синхронно корелює зі зростанням вхідного трафіку (`http_requests_total`).
</details>

<details markdown="1">
<summary><b>3. Що являють собою Baggage Items у стандарті W3C / OpenTelemetry і які ризики несе їх надмірне використання?</b></summary>

**Baggage** — це пари ключ-значення з контекстною інформацією (`tenant_id=enterprise_42`), які додаються до трейсу та автоматично передаються в мережевих заголовках крізь **усі наступні сервіси графа викликів**.

Збереження в Baggage великих обсягів даних призводить до розростання розміру HTTP-заголовків. Оскільки вони дублюються на кожному міжсервісному запиті, це створює відчутний паразитний трафік у мережі та провокує відмови вебсерверів через переповнення буферів (`HTTP 431 Request Header Fields Too Large`).
</details>

<details markdown="1">
<summary><b>4. Чому під час аналізу CrashLoopBackOff перевірка коду завершення процесу (Exit Code) є першочерговою дією?</b></summary>

Код завершення чітко класифікує категорію збою:
* **Exit Code 0:** Процес завершився штатно (контейнер помилково запустили як довготривалий сервіс без foreground-процесу).
* **Exit Code 1 / 2:** Помилка в прикладному коді (необроблений виняток, синтаксична помилка, збій скрипту запуску).
* **Exit Code 137 ($128 + 9$):** Процес примусово зупинено сигналом SIGKILL через вичерпання ліміту оперативної пам'яті (**OOMKilled**).
* **Exit Code 143 ($128 + 15$):** Процес коректно зупинено сигналом SIGTERM від Kubelet під час планового виселення або оновлення версії.
* **Exit Code 139 ($128 + 11$):** Помилка сегментації пам'яті (**Segmentation Fault** у скомпільованих бінарних модулях).
</details>

## 6. Практичний місток: Зв'язок із лабораторним курсом

Матеріали цієї лекції є прямою інструкцією до виконання **Етапу 5 (Chaos & FinOps)** нашого курсу:

* **Впровадження OpenTracing / W3C Headers у симулятор:**
  * Студенти модифікують воркери Монте-Карло, прокидаючи `traceparent` заголовок від API-шлюзу до обчислювальних потоків реактора та розрахунків ліній IEEE-118.
  * У **Jaeger UI** візуалізується повний граф: розбиття загального часу симуляції на генерацію випадкових чисел, розрахунок матриць та серіалізацію результатів.
* **Трасування крізь процесорну межу в Python (`multiprocessing.Pool`):**
  * *Системний бар'єр:* Для обходу GIL симулятор використовує процеси (`multiprocessing.Pool`). Бібліотеки OpenTelemetry за замовчуванням тримають `SpanContext` у контекстних змінних (`contextvars` / ThreadLocal). При виклику `Pool.map` нові процеси ОС створюються через `fork()`: пам'ять копіюється, проте зв'язок трасування втрачається автоматично.
  * *Рішення для лабораторного коду:* Функція воркера `simulate_trials_chunk` повинна приймати `traceparent` як явний строковий аргумент у кортежі `args`. Всередині воркера виконується ручне відновлення контексту:
    ```python
    from opentelemetry.trace.propagation.tracecontext import TraceContextTextMapPropagator

    # Ручна десеріалізація контексту в ізольованому процесі воркера
    context = TraceContextTextMapPropagator().extract(carrier={"traceparent": traceparent_str})
    ```
  * Тільки після цього спани, створені воркерами на ядрах CPU, відобразяться в Jaeger як дочірні вузли головного запиту від API Gateway.
* **Бенчмаркінг перцентилів у стрес-тестах:**
  * При ін'єкції збоїв (через **Toxiproxy** або генерацію високого I/O навантаження Noisy Neighbor) студенти фіксують не середній час розрахунку, а графіки **P50 vs P99 latency**.
  * Оцінюється ефект впливу «важкого хвоста» на загальну пропускну здатність (Throughput) кластера.

## Контрольні питання

<details markdown="1">
<summary><b>1. Чому використання Tail-based Sampling у великих системах вважається значно ефективнішим за Head-based Sampling?</b></summary>

При **Head-based Sampling** система обирає, чи записувати трейс, на самому початку (на рівні API Gateway), коли ще невідомо, чи завершиться запит успішно. Якщо ймовірність збою становить 0.01%, при 1% вибірці більшість критичних помилок ніколи не потрапить у моніторинг. 

**Tail-based Sampling** тимчасово тримає спани в оперативній пам'яті колектора до повного завершення ланцюжка викликів. Це дозволяє зберегти **100% усіх повільних запитів (P99) та запитів із помилками (HTTP 500)**, одночасно відкидаючи 99.9% одноманітних успішних викликів, мінімізуючи навантаження на сховище.
</details>

<details markdown="1">
<summary><b>2. Як відрізнити за системними метриками поступовий витік пам'яті (Memory Leak) від раптового короткочасного сплеску навантаження перед тим, як контейнер вб'є OOM-killer (Exit Code 137)?</b></summary>

При **Memory Leak** графік споживання пам'яті (`container_memory_working_set_bytes`) формує характерну монотонно зростаючу «пилкоподібну» криву (Sawtooth pattern), яка не повертається до базового рівня навіть у періоди нічного спаду активності користувачів. 

При **раптовому сплеску навантаження** лінія пам'яті є рівною і стабільною, після чого виникає практично вертикальний стрибок за кілька секунд, що корелює з одночасним зростанням лічильника вхідних запитів (`http_requests_total`).
</details>

<details markdown="1">
<summary><b>3. Що являють собою Baggage Items у стандарті OpenTelemetry / W3C і чому безконтрольне їх використання може призвести до деградації мережі?</b></summary>

**Baggage** — це пари ключ-значення (контекстні дані, наприклад `account_type=vip`), які прикріплюються до трейсу і автоматично прокидаються в HTTP/gRPC-заголовках крізь **усі наступні мікросервіси в ланцюжку**. 

Якщо розробники починають запихати в Baggage великі структури даних (наприклад, токени користувача, кошики товарів чи важкі контексти), розмір HTTP-заголовків зростає до десятків кілобайтів. Оскільки ці заголовки передаються на кожному міжсервісному виклику, мережевий оверхед мультиплікується, викликаючи падіння пропускної здатності та помилки переповнення буферів серверів (`HTTP 431 Request Header Fields Too Large`).
</details>

<details markdown="1">
<summary><b>4. Чому при виникненні CrashLoopBackOff перевірка коду повернення процесу (Exit Code) є найшвидшим способом визначити напрям пошуку проблеми?</b></summary>

Тому що Exit Code чітко розмежовує апаратні, системні та прикладні помилки:
* **Exit Code 0:** Процес успішно завершив роботу (контейнер був створений як Job замість Deployment, або завершився через відсутність foreground-процесу).
* **Exit Code 1 / 2:** Помилка в прикладному коді (неперехоплений Exception, синтаксична помилка, падіння скрипту ініціалізації).
* **Exit Code 137 ($128 + 9$):** Процес вбито сигналом SIGKILL через вичерпання ліміту пам'яті (**OOMKilled**).
* **Exit Code 143 ($128 + 15$):** Процес штатно прибито сигналом SIGTERM від Kubelet під час виселення чи деплою.
* **Exit Code 139 ($128 + 11$):** Помилка сегментації пам'яті (**Segmentation Fault** у бінарному C/C++ коді).
</details>
