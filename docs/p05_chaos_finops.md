## Питання для розминки

**Питання 1: Чому для пошуку вузьких місць у мікросервісах недостатньо звичайних логів, і яку проблему вирішує наскрізний Trace ID?**

Користувач натискає кнопку запуску розрахунку, і запит проходить через API Gateway, чергу задач та три мікросервіси. Один зі ста запитів зависає на 5 секунд. У кластері працюють десятки реплік кожного сервісу, які генерують мегабайти текстових логів щохвилини. Чому знайти причину зависання через звичайний пошук у логах (наприклад, `grep` або Elasticsearch) майже неможливо?

<details markdown="1">
<summary><b>Дізнатися відповідь</b></summary>

Логи фіксують **ізольовані події всередині окремих процесів**, але не зберігають контекст подорожі запиту крізь розподілену систему.

Коли одночасно обробляються сотні запитів, рядки в централізованому сховищі логів перемішуються. Знаючи лише приблизний час зависання, неможливо відокремити логи проблемного клієнта від успішних дій інших користувачів.

**Розподілене трасування (Distributed Tracing)** пов'язує всі етапи в єдиний контекст:
1. **Trace ID:** Шлюз генерує унікальний ідентифікатор транзакції і прокидає його через усі сервіси в заголовках викликів (W3C TraceContext).
2. **Span:** Кожна операція фіксує свій час початку та тривалість.

В інтерфейсі системи трасування (Jaeger) інженер бачить наскрізну часову шкалу (водоспад викликів). Вузьке місце підсвічується автоматично: одразу видно, який саме мікросервіс або запит до бази даних забрав 5 секунд.

</details>

**Питання 2: Чому мережеві таймаути не рятують мікросервіс від падіння при відмові зовнішньої залежності, і як принцип Fail-Fast реалізується через Circuit Breaker?**

Сервіс розрахунків робить HTTP-запити до зовнішньої бази даних із таймаутом у 10 секунд. База зазнає аварії і перестає відповідати взагалі. До сервісу розрахунків продовжує надходити звичайний потік користувачів (100 запитів на секунду). Менш ніж за пів хвилини сервіс розрахунків також виходить із ладу і перестає відповідати навіть на перевірки здоров'я Kubernetes (`/health`). Чому таймаут у 10 секунд не захистив систему?

<details markdown="1">
<summary><b>Дізнатися відповідь</b></summary>

Таймаут обмежує час очікування одного запиту, але змушує клієнта утримувати відкрите з'єднання та блокувати потік виконання (**Thread / Connection Pool Starvation**).

За інтенсивності 100 запитів на секунду і затримці 10 секунд у системі одночасно накопичується до 1000 завислих з'єднань. Пул потоків сервера вичерпується. Застосунок більше не може обробити навіть локальну перевірку Kubernetes Liveness Probe, і kubelet перезапускає контейнер.

Для захисту застосовують патерн **Circuit Breaker (запобіжник)**, що реалізує принцип **Fail-Fast (миттєва відмова)**:
1. **Стан Closed:** Запити проходять у звичайному режимі.
2. **Стан Open:** Коли кількість помилок чи таймаутів перевищує поріг (наприклад, 5 поспіль), запобіжник розмикає коло. Усі наступні виклики миттєво відхиляються за 1 мілісекунду без жодної спроби достукатися до мертвої залежності.
3. **Результат:** Пул потоків залишається вільним, пам'ять не вичерпується, а сервіс продовжує виконувати незалежні операції.

</details>

**Питання 3: Чому обчислювальний воркер, у якому коректно реалізовано перехоплення сигналу SIGTERM, усе одно залишає битий файл стану при виселенні Spot-ноди?**

Воркери пакетних розрахунків перевели на Spot-інстанси. Інженери реалізували в коді обробник сигналу `SIGTERM`: щойно хмара надсилає сповіщення про вилучення машини, воркер зупиняє цикл і починає серіалізувати проміжний стан розрахунків у JSON-файл на диску.

Проте під час першого ж виселення ноди новий воркер, піднятий планувальником на іншому сервері, аварійно впав під час спроби завантажити збережений стан (`JSONDecodeError: Unterminated string`). 

Чому файл виявився обірваним на середині, якщо перехоплювач `SIGTERM` відпрацював штатно?

<details markdown="1">
<summary><b>Дізнатися відповідь</b></summary>

Причина полягає у взаємодії життєвого циклу Pod у Kubernetes та дискового I/O:

1. **Жорсткий ліміт очікування (`terminationGracePeriodSeconds`):** 
Після надсилання `SIGTERM` kubelet чекає завершення процесу лише визначений час (за замовчуванням 30 секунд). Якщо операція збереження великого стану триває довше, kubelet надсилає неперехоплюваний сигнал **`SIGKILL`**. Процес гине миттєво, обриваючи запис файлу на середині.

2. **Неатомарний запис на диск:** 
Прямий запис у цільовий файл (`with open("checkpoint.json", "w")`) руйнує дані при аварійній зупинці. На диску залишається пошкоджений файл часткового розміру.

**Архітектурне рішення:**
- **Узгодження тайм-аутів:** Значення `terminationGracePeriodSeconds` у маніфесті Pod налаштовують під розмір даних, але залишають меншим за вікно сповіщення хмарного провайдера (наприклад, 25 с за умови 30-секундного сповіщення хмари).
- **Атомарний запис (Atomic Write):** Стан спочатку записується в тимчасовий файл (`checkpoint.tmp`), буфер синхронізується з диском (`f.flush()`, `os.fsync()`), після чого файл перейменовується однією атомарною операцією файлової системи (`os.replace`). При загибелі процесу під час запису новий воркер підхопить попередній валідний чекпоінт.

</details>

## Контекст індустрії: Від наївного коду до стійкої хмарної системи

Розподілена система ніколи не перебуває в ідеальному стані. У великому кластері щохвилини відмовляють мережеві інтерфейси, перезавантажуються Spot-сервери або з'являються задачі-диверсанти, які здатні покласти весь пул воркерів.

| Інженерний аспект | Наївний підхід (Dev) | Хмарний SRE & FinOps (Prod) |
| :--- | :--- | :--- |
| **Стійкість до збоїв** | Збій воркера вважається рідкістю | Воркери постійно гинуть і рвуться (збій є нормою) |
| **Політика повторів** | Повтори за фіксованим інтервалом (ризик Retry Storm) | Full Jitter + Circuit Breaker |
| **Обробка збійних задач** | Черга нескінченно повторює «отруйний» батч | Dead Letter Queue (DLQ) ізолює збій |
| **Модель витрат** | On-Demand сервери за 100% ціни | Spot-ноди (знижка 80–90%) + чекпоінти |
| **Діагностика** | Логи читають вручну через `grep` | Наскрізне трасування (Jaeger UI) |


**Chaos Engineering** — це дисципліна перевірки гіпотез стійкості через контрольовану ін'єкцію відмов у систему.

1. Розгорнути повноцінний бекенд розподіленого трасування **Jaeger** у Kubernetes (Minikube / k3s) або через Docker Compose.

3. Дослідити феномен **"отруйної пігулки" (Poison Pill Task)** у розподіленій черзі, локалізувати збійний спан у Jaeger та налаштувати ізоляцію через **Dead Letter Queue (DLQ)**.
4. Змоделювати шторм ретраїв (**Retry Storm / Thundering Herd**) при падінні залежності та ліквідувати резонанс за допомогою **Circuit Breaker та Full Jitter**.
5. Реалізувати та протестувати механізм **Graceful Checkpointing** при симуляції виселення Spot-інстансу за сигналом `SIGTERM`.
6. Змоделювати мережевий джитер, розрахувати перцентилі затримки **P50, P90, P95, P99** та знайти аномальні спани в інтерфейсі Jaeger.

### Формат контексту W3C TraceContext
Для зв'язування викликів між різними процесами та контейнерами використовується стандартний заголовок HTTP або метаданих:

$$\texttt{traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01}$$

- `00` — версія стандарту.
- `4bf92f3577b34da6a3ce929d0e0e4736` — глобальний **Trace ID** (16 байтів), спільний для всього ланцюжка.
- `00f067aa0ba902b7` — ідентифікатор батьківського спану **Parent Span ID** (8 байтів).
- `01` — прапорець трасування (семпльований запит).

## 4. Інструментування коду через OpenTelemetry

Усі експерименти спираються на модуль [`source/chaos-finops/tracer.py`](https://github.com/vplanto/cloud_grid/blob/main/source/chaos-finops/tracer.py). Він інкапсулює роботу з бібліотеками OpenTelemetry та містить захисний fallback-режим на випадок відсутності сторонніх пакетів.

### Налаштування середовища (.venv) та встановлення залежностей

Для ізоляції бібліотек OpenTelemetry створіть та активуйте віртуальне оточення Python:

```bash
# 1. Створення віртуального оточення
python3 -m venv .venv

# 2. Активація віртуального оточення (Linux / macOS):
source .venv/bin/activate
# (для Windows PowerShell: .venv\Scripts\Activate.ps1)

# 3. Оновлення pip та встановлення пакетів:
pip install --upgrade pip
pip install -r source/chaos-finops/requirements.txt
# (якщо ви вже перебуваєте в каталозі source/chaos-finops/ — pip install -r requirements.txt)
```

### Патерн створення вкладених спанів у коді

```python
from tracer import get_tracer, start_span, inject_trace_context

# 1. Ініціалізація трейсера для поточного сервісу
tracer = get_tracer("power-grid-worker")

# 2. Створення батьківського спану для всієї пачки задач
with start_span("batch.process", {"batch.size": 1000, "grid.model": "ieee118"}) as root_span:
    for trial_id in range(10):
        # 3. Створення дочірнього спану для конкретної траєкторії
        with start_span("trial.simulate", {"trial.id": trial_id}) as child_span:
            # Обчислення каскаду
            run_matrix_math()
```

У разі виникнення винятку метод `record_exception()` автоматично фіксує стек помилки у спані та встановлює статус `StatusCode.ERROR`.

## 5. SRE-практикум Chaos Engineering: Ін'єкція відмов

#### Крок 2. Локалізація отруйної задачі в Jaeger UI та захист через DLQ:

## 8. Контрольні запитання для захисту Етапу 5 (КТ 4)

**Питання 1: Чому контекст трасування (TraceContext) втрачається при передачі задачі в асинхронний ThreadPool або брокер повідомлень (Kafka/RabbitMQ), якщо не передати його явно?**

<details markdown="1">
<summary><b>Дізнатися відповідь</b></summary>

За замовчуванням більшість бібліотек трасування (зокрема OpenTelemetry у Python та Java) зберігають активний `SpanContext` у локальній пам'яті потоку (**Thread-Local Storage** або контекстних змінних `contextvars`).

Коли задача передається в інший потік, процес або відправляється як повідомлення в чергу по мережі, пам'ять потоку не копіюється автоматично. Дочірній воркер не бачить батьківського контексту і починає новий трейс із випадковим `TraceID`. 

Для збереження зв'язку розробник зобов'язаний виконати **Inject** заголовка W3C (`traceparent`) у метадані повідомлення на стороні відправника, а на стороні отримувача викликати **Extract** перед початком обробки задачі.

</details>

**Питання 2: Як розпізнати "отруйну пігулку" (Poison Pill Task) у черзі за допомогою Jaeger, і чому без Dead Letter Queue це спричиняє Head-of-Line Blocking усього пулу воркерів?**

<details markdown="1">
<summary><b>Дізнатися відповідь</b></summary>

"Отруйна пігулка" — це задача, обробка якої викликає аварійне падіння воркера (наприклад, через збій десеріалізації або OOM Killer).

Якщо в черзі увімкнено автоматичний ретрай без ізоляції, після падіння першого воркера задача повертається на початок черги. Наступний вільний воркер бере її в роботу і також миттєво гине. За кілька секунд весь пул реплік потрапляє в аварійний стан `CrashLoopBackOff`. 

Решта валідних задач у черзі не можуть бути оброблені — виникає **Head-of-Line Blocking (блокування початку черги)**.

У **Jaeger UI** така аномалія виявляється через пошук серії незавершених або червоних спанів `worker.process_task` з однаковим ідентифікатором задачі (`task.id`). Рішення полягає у встановленні ліміту спроб (`MaxRetries`) та автоматичному перенаправленні задачі-диверсанта в ізольований карантин — **Dead Letter Queue (DLQ)**.

</details>

**Питання 3: Як формула Янга/Дейлі захищає від фінансових збитків при роботі зі Spot-інстансами?**

<details markdown="1">
<summary><b>Дізнатися відповідь</b></summary>

Формула визначає точну математичну точку рівноваги між двома протилежними статтями витрат:
1. **Витрати на часті чекпоінти:** плата за I/O, навантаження CPU та вартість кожного виклику API об'єктного сховища (S3 PUT).
2. **Витрати на перезапуск при аварії:** у разі виселення ноди без збереженого стану втрачається вся робота, виконана з моменту останнього збереження (у середньому половина інтервалу tau / 2).

Формула tau ≈ √(2 · delta · M) мінімізує сумарні втрати часу та коштів, розраховуючи періодичність, за якої сума витрат на операції збереження дорівнює математичному очікуванню втрат від відновлення після збоїв.

</details>

**Питання 4: Яка принципова різниця між Head-based та Tail-based семплюванням у системах розподіленого трасування?**

<details markdown="1">
<summary><b>Дізнатися відповідь</b></summary>

- **Head-based Sampling:** Рішення про те, записувати трейс чи викинути його, ухвалюється на самому початку транзакції (наприклад, на API Gateway) випадковим чином (наприклад, для 2% трафіку). Перевага: мінімальне навантаження на мережу. Недолік: якщо збій чи аномалія сталися на 98% незаписаних запитів, інформація про аварію втрачається назавжди.
- **Tail-based Sampling:** Усі спани тимчасово буферизуються в пам'яті колектора (OpenTelemetry Collector). Рішення ухвалюється **після завершення всього запиту**: транзакції з помилками (HTTP 5xx, спани зі статусом Error) та високою затримкою (P99 > 2 с) зберігаються на 100%, тоді як типові успішні запити зберігаються на рівні 0.1%. Це гарантує повну спостережуваність усіх системних аномалій.

</details>

## 9. Завершення роботи та зупинка оточення (Teardown & Cleanup)

Після виконання експериментів та генерації звіту `finops_report.json` зупиніть фонові компоненти, щоб вивільнити оперативну пам'ять та ресурси процесора.

### 9.1. Зупинка фонового прокидання портів
Якщо запускалося прокидання портів у фоновому режимі:
```bash
pkill -f "port-forward"
```

### 9.2. Якщо використовувався Docker Compose (Варіант Б)
Зупиніть та видаліть контейнер Jaeger:
```bash
docker compose -f source/chaos-finops/docker-compose.yml down
# (або просто: docker stop jaeger-observability)
```

### 9.3. Якщо використовувався Minikube (Варіант А)
1. Видаліть ресурси Jaeger із кластера:
```bash
kubectl delete -f source/chaos-finops/jaeger.yaml
```

2. Зупиніть локальний кластер Minikube (це вивільнить виділені під VM 3 ГБ оперативної пам'яті):
```bash
minikube stop
```

### 9.4. Деактивація віртуального оточення Python
```bash
deactivate
```
